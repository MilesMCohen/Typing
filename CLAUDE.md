# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server (`--host`, binds all interfaces). Reads `PORT` from the environment if set, otherwise defaults to 5173.
- `npm run build` — production build to `dist/`.
- `npm run preview` — serve the built `dist/` output locally.
- `npm run test` — run the Vitest unit test suite once (no watch mode).

There is no linter configured in this project.

## Architecture

This is a React + Vite project (migrated from an initial vanilla-JS scaffold) deployed to GitHub Pages, with Firebase providing the only backend/data-persistence layer. There is no server of any kind — all Firebase calls happen directly from client-side JS in the browser.

- **Entry point**: `index.html` mounts `src/main.jsx`, which renders `src/App.jsx`. `App.jsx` is a screen router (`menu` / `game` / `results` / `test-select` / `test-game` / `test-results` / `settings`, animated with Framer Motion's `AnimatePresence`) between `src/Menu.jsx`, `src/Game.jsx`, `src/Results.jsx`, `src/TestSelect.jsx`, `src/TestResults.jsx`, and `src/Settings.jsx`.
- **Game**: a progressive touch-typing game. `src/lessons.js`'s `WORD_BANK` is a single flat, alphabetical list of ~4,200 everyday fourth-grade words (lowercase a-z only — capitals/digits/symbols are added by the generator later, so raw punctuation here would just make a word ineligible until those stages). It's the word-bank data source for `src/progression.js`, which filters it down to whatever letters are currently unlocked — so it's deliberately letter-agnostic, not split by keyboard row. (It replaced an earlier 3-list `LESSONS` structure whose Home Row / Upper Row / Full Keyboard labels no longer drove anything.) `lessons.js` also exports the layout helpers `WORDS_PER_LINE` / `LINES_PER_ROUND` / `randomWords()`. `src/typing.js` holds the pure scoring logic (`getCharStatuses`, `computeAccuracy`, `computeWpm`) used by `Game.jsx` to render live per-character feedback and compute results — kept separate from the component specifically so it's unit-testable without rendering React. `src/typing.test.js` and `src/lessons.test.js` cover this logic; expect these to need updating as the game design changes. `Game.jsx` also exposes an "Exit (Esc)" control (`onExit` prop) so a lesson or test can be abandoned mid-round — since `onComplete` only ever fires on a full, exact match, exiting never records any stats, i.e. it's as if the round never happened.
- **Adaptive lesson progression**: `src/progression.js` replaces the old fixed 3-lesson picker with a single continuous adaptive track, driven entirely by pure functions (unit-tested in `src/progression.test.js`). `KEY_STAGES` unlocks 1-2 lowercase letters at a time (home row first). Within each row, the index-finger "reach" pair typed by sliding off the home column (g/h, t/y, b/n) is deliberately introduced *last*, after an empty consolidation stage that repeats a round on that row's easier keys — g/h and t/y look like they belong with the rest of their row, but they require real finger movement off the home position, so they get their own dedicated (and delayed) stage rather than being bundled in at the same pace. Once the full alphabet is unlocked, three more cumulative stages layer on capitals, numbers, and symbols (`CAPITALS_STAGE` / `NUMBERS_STAGE` / `SYMBOLS_STAGE`, up to `MAX_STAGE`); `stageLabel()` maps each of these 20 stages to a human name from `STAGE_NAMES` (e.g. `"Home Row: F & J"`, `"Full Keyboard"` for `MAX_STAGE`) rather than a numbered "Level N", so an advanced typer landing on the last stage sees what they've actually unlocked instead of an arbitrary-looking ceiling. `buildLessonPlan(history, wpmTarget)` looks at up to the last 5 lesson results (`MAX_HISTORY`) and calls `decideNextStage()` to advance a stage, hold the current stage while emphasizing `weakGroups()` (high-error-rate letter groups), or regress a stage (accuracy too low, or speed dropped sharply vs. the recent best). **Advancing requires both accuracy ≥95% and average wpm at or above `wpmTarget`** — speed is treated as the primary gate (not just accuracy), so a kid who already knows the content but is slow gets a `"hold-speed"` direction instead of unlocking new letters; `"mastered"` only fires once every stage is unlocked *and* the wpm target is met. `generateRoundWords()` samples real words from the word bank once enough exist for the unlocked letters, weighting toward weak letters, and falls back to synthetic letter drills (e.g. `"fjf jdj"`) for the earliest stages where too few real words are spellable; once capitals/numbers/symbols stages are reached it also capitalizes words and sprinkles in digit/symbol tokens.
- **Per-row stats**: single letters, or even per-finger-pair groups, only come up a handful of times per round — too thin to say anything meaningful quickly. Accuracy/speed stats are instead bucketed into 7 groups: physical keyboard row for lowercase letters (home/top/bottom — the same three-row split `KEY_STAGES` progresses through and `STAGE_NAMES` labels, e.g. "Home Row: ...", "Top Row: ...", "Bottom Row: ..."), a 0-9 group, and — since touch typing always presses Shift with the hand *opposite* the key being shifted — Capitals and Punctuation each split into a left-shift and right-shift group. `groupForChar()` computes a letter's hand from a hardcoded `LEFT_HAND_LETTERS` set and takes the opposite for any uppercase char; punctuation (`SYMBOL_INFO`) records which hand's key each symbol comes from and whether it's actually shifted (e.g. `,` `.` `'` `-` `;` are unshifted and typed outright by the right hand; `!` is Shift+1 where "1" is a left-hand key, so it counts as right-shift; `?`/`:` are Shift+`/`/`;`, both right-hand keys, so they count as left-shift) — so a group like "Capitals (Right Shift)" always means "the right pinky is the one doing the work here," whether that's holding shift for a left-hand letter or pressing shift for a left-hand-based symbol. `Game.jsx` timestamps each keystroke (`keyTimestampsRef`) and turns them into per-character ms via `computeCharDurations()` (`typing.js`), then `getLetterStats(target, typed, durationsMs)` (`progression.js`) accumulates attempts/correct/totalMs per group and passes the result up through `onComplete` as `letterStats`. `groupBreakdown(letterStats)` turns that into a display list (accuracy % plus a derived wpm per group, `null` until a group has any timed attempts); `weakGroups()` (used internally by `buildLessonPlan` to bias word selection, expanding groups back into individual characters via `lettersInGroup` — the capitals/punctuation groups have no specific letters of their own, so they contribute no extra word-selection weighting even when flagged weak) and the display list both key off the same grouping so what's called out as weak matches what the round actually drills. `App.jsx` appends each result to `history` and persists it, along with `wpmTarget`, to `users/{uid}` in Firestore for signed-in users (in-memory/session-only for guests — no rules changes needed, since it's just new fields on the existing per-user document). `Results.jsx` displays the lesson's wpm/accuracy alongside the per-group accuracy/speed breakdown, a wpm-vs-target progress bar, and the advance/hold-speed/hold/regress/mastered message, both for fun and to make the adaptive behavior debuggable.
- **Speed target**: `GRADE_WPM_TARGETS` in `progression.js` maps 1st grade through adult proficiency levels (1st–8th grade, High school, Adult average, Proficient, Expert) to benchmark wpm values, from 5 up to 100 (`DEFAULT_WPM_TARGET` is 20, the 4th-grade preset) — the list isn't kid-only, an adult practicing alongside their kid can pick a target near their own speed too. `Settings.jsx` lets the user pick one, which `App.jsx` stores in `wpmTarget` state and persists to `users/{uid}.wpmTarget` for signed-in users; it's threaded into `buildLessonPlan` so the advance/hold-speed decision above is relative to whichever target is currently selected.
- **Placement test**: `TEST_LEVELS` in `progression.js` defines 10 named difficulty tiers (a few letters through all keys with symbols), each mapped to a `stageIndex` on the same scale used by adaptive play. Three of them ("Most of the home row", "Home row and most of the top row", "Most letters") sit right before a row's harder g/h, t/y, or b/n reach pair unlocks, mirroring `KEY_STAGES`' own consolidation stages, so placement can land just before or after the hardest part of a row rather than only at whole-row boundaries. `TestSelect.jsx` lets the user pick a tier, `buildTestRound()` generates a round for it, and on completion `evaluateTestResult(accuracy, wpm, wpmTarget)` suggests increasing, decreasing, or keeping the level in `TestResults.jsx`. Passing requires wpm at or above `minWpmForTarget(wpmTarget)` — the wpm of the grade *one below* the current speed goal (e.g. a 20wpm/4th-grade target requires 12+/3rd-grade wpm just to pass) — in addition to accuracy ≥75%; increasing requires both ≥95% accuracy and wpm at or above the full target. A test result **replaces** `history` in `App.jsx` (rather than appending to it) — that's the "reset/recalibrate" behavior — so the next adaptive lesson picks up from wherever the test placed her.
- **SnowLeopard animation**: `src/SnowLeopard.jsx` renders a PixiJS (`pixi.js`, imperative canvas API, not `@pixi/react`) side-scrolling scene — parallax mountain layers, falling snow, and a leopard that jumps crag-to-crag as a `progress` prop (0–1) advances, reaching a snow-capped peak with food at `progress === 1`. It manages its own `Application` lifecycle in a `useEffect` (async `app.init()`, manual `app.destroy()` on unmount) since Menu/Game/Results mount and unmount it repeatedly via `AnimatePresence`. Used decoratively (idle) in `Menu.jsx`, live-tied to typing progress in `Game.jsx`, and at `progress={1}` in `Results.jsx`. The deterministic terrain/jump math (`buildCrags`, `leopardPosition`) lives in `src/terrain.js`, split out from the Pixi drawing code specifically so it's unit-testable — same rationale as `typing.js` below.
- **Testing**: Vitest is configured with no separate config file (it reads `vite.config.js` automatically). Tests are colocated as `*.test.js` next to the module they cover, and only exercise plain functions (no component rendering, no jsdom) so the suite stays fast — this is the primary way to verify game-logic changes, faster than manually exercising the UI. `src/lessons.js`'s `splitIntoLines` (used by `Game.jsx` to break the flat typing target into display rows) and `src/terrain.js`'s crag/jump math are covered this way; when adding new non-visual logic (scoring, layout math, animation curves), prefer extracting a pure function and testing it here over relying on the browser preview.
- **Firebase**: `src/firebase.js` initializes the Firebase app and exports `auth` (Firebase Auth) and `db` (Firestore). The `firebaseConfig` object is hardcoded there intentionally — Firebase's web config is not a secret (security comes from Firestore/Auth rules, not from hiding this object), so there is deliberately no `.env`/env-var indirection for it.
- **Data model**: Firestore stores per-user data at `users/{uid}`, keyed by the Firebase Auth UID. `firestore.rules` restricts each document to `request.auth.uid == userId`. **Rules changes must be manually pasted into the Firebase console's Firestore Rules tab and published** — there is no CI/CD step or Firebase CLI deploy wired up for `firestore.rules`; the file in this repo is the source of truth but is not automatically applied.
- **Auth**: Google sign-in via `signInWithPopup`. Any new domain the app is served from must be added to Firebase Auth's Authorized domains list in the console, or sign-in will fail there (`localhost` is allowed by default; `milesmcohen.github.io` has been added for production).
- **Deployment**: `.github/workflows/deploy.yml` builds and deploys `dist/` to GitHub Pages on every push to `main`, via `actions/upload-pages-artifact` + `actions/deploy-pages`. `vite.config.js` sets `base: "/Typing/"` to match the GitHub Pages path (`https://milesmcohen.github.io/Typing/`). Pages itself is configured (once, via the GitHub API/console) to build from GitHub Actions rather than a branch.
- **GitHub account**: this repo lives under the `MilesMCohen` GitHub account, which is a different `gh` CLI account than the machine's default (`mcohen_adobe`). Running `gh`/`git` commands from this repo's directory picks up `MilesMCohen` automatically via `direnv` — `.envrc` (gitignored, holds `GH_TOKEN`) is loaded per-directory; see `.envrc.example` for the template. Run `direnv allow` after creating `.envrc` locally.

## Verifying changes

Prefer `npm run test` over the Claude Code browser preview for verifying changes. Whenever logic can be expressed as a pure function (scoring, layout/offset math, animation curves like `terrain.js`'s crag/jump interpolation), extract it out of the component/rendering code and cover it with a Vitest test, per the pattern above — this is faster to run and keeps working even when a browser preview isn't available. Only spin up the preview for changes that are inherently visual/interactive and can't be meaningfully asserted on in a unit test (layout, animation feel, colors, click flows) — and even then, prefer the smallest check that answers the question (e.g. inspecting DOM/canvas state) over a full manual click-through.
